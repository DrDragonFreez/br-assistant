# Механизм поиска и формирования ответов

## Подготовка базы знаний

### Нарезка с привязкой к пунктам

Обычный рекурсивный сплиттер режет текст по числу символов и теряет
границы пунктов. Для нормативного документа это неприемлемо: ответ обязан
ссылаться на конкретное положение.

Реализован собственный сплиттер (`backend/app/rag/chunker.py`), работающий
в три прохода:

1. **Разметка структуры** — регулярные выражения находят заголовки
   разделов, номера пунктов (`3.4.2`) и приложений.
2. **Группировка** — абзацы и подпункты собираются в блоки по границам пунктов.
3. **Приведение к размеру** — длинные блоки режутся по предложениям с
   перекрытием, короткие соседние объединяются в пределах одного раздела.

Каждый фрагмент сохраняет: номер пункта, заголовок главы, номер
приложения, номер страницы и структурный путь. Номера пунктов
дополнительно дублируются в начале текста фрагмента — это заметно улучшает
попадание при запросах вида «что сказано в пункте 3.4».

**Объединённые пункты.** Короткий пункт («3.1. Общие положения.») по
отдельности бесполезен для поиска и присоединяется к следующему. При этом
фрагмент хранит **список всех пунктов**, текст которых в него попал
(`clause_numbers`, в payload Qdrant — поле `clauses` с отдельным индексом),
а основным адресом становится пункт, которому принадлежит большая часть
текста. Без этого ответ про требование из п. 3.4 цитировался бы как
п. 3.1, а поиск по номеру пункта не нашёл бы положение вовсе. Поиск по
номеру проверяет оба поля, критик считает допустимыми все номера
фрагмента, а подпись источника перечисляет их: «п. 3.1, 3.4».

**Водяные знаки.** Загрузчик отбрасывает символы светлой заливки
(`PDF_DROP_WATERMARK`). На учебной инструкции кейса диагональная надпись
«УЧЕБНЫЙ ПРИМЕР» давала 3570 лишних символов, которые pdfplumber вставлял
внутрь слов: «законоИдательство», «стрОуктурные». Это портило и
лексический поиск, и эмбеддинги, и цитату, которую видит сотрудник —
318 искажённых слов на документ против нуля после фильтра.

### Векторизация

На каждый фрагмент строятся два вектора:

- **плотный** — bge-m3, 1024 измерения, косинусная метрика;
- **разреженный** — BM25 по собственному словарю, собранному на корпусе
  инструкции (`backend/app/rag/bm25.py`). Токенизатор сохраняет номера
  пунктов целиком: `3.4.2` не разбивается по точкам.

## Поиск

### Гибридный режим

Запрос выполняется одновременно по обоим векторам, результаты объединяются
через Reciprocal Rank Fusion на стороне Qdrant. Плотный поиск находит
перефразированные вопросы, разреженный — точные формулировки и номера.

RRF работает с позициями документов в двух выдачах, а не с их оценками,
поэтому весов у плотной и разреженной частей нет: настроек вида
«dense 0.7 / sparse 0.3» в конфигурации нет намеренно, они создавали бы
видимость управления тем, чего алгоритм не использует.

Словарь BM25 собирается при индексации и сохраняется на диск: индексация
идёт в процессе Celery-воркера, а запросы обслуживает процесс API. Файл
состояния перечитывается по времени изменения — иначе после `make index`
работающий сервис продолжал бы искать по старому словарю, молча
деградировав до плотного поиска.

### Приоритет явных ссылок

Если в обращении есть прямая ссылка на пункт или приложение, эти фрагменты
извлекаются отдельным запросом по точному значению и ставятся в начало
выдачи независимо от семантической близости.

### Фильтрация по правам

Фильтр по грифу документа уходит **в сам запрос к Qdrant**. Фрагменты,
закрытые для роли пользователя, не попадают ни в выдачу, ни в контекст
языковой модели. Это снимает класс рисков, связанных с утечкой через
промпт.

### Переранжирование

Top-20 кандидатов переранжируются cross-encoder'ом bge-reranker-v2-m3 и
усекаются до top-5. Логиты нормализуются сигмоидой — это даёт сопоставимые
между запусками проценты релевантности, которые показываются сотруднику.

## Формирование ответа

### Три барьера против выдумывания

1. **До генерации.** Если лучший фрагмент не дотягивает до порога
   `ANSWER_MIN_RELEVANCE`, модель не вызывается вовсе: сразу выдаётся
   честный отказ. Это и быстрее, и надёжнее, чем надеяться на промпт.
2. **В промпте.** Модели прямо запрещено использовать что-либо, кроме
   переданных фрагментов; при недостатке контекста она обязана вернуть
   фиксированный маркер `НЕТ_В_БАЗЕ_ЗНАНИЙ`.
3. **После генерации.** Критик (`backend/app/agents/critic.py`) выполняет
   детерминированную сверку: каждый упомянутый в ответе пункт проверяется
   на присутствие в контексте. Ссылка на несуществующий пункт выявляется
   **гарантированно, без участия модели**. Дополнительно модель-критик
   ищет утверждения, не подтверждённые источниками.

При отрицательном вердикте ответ перегенерируется один раз с добавлением
замечаний в промпт. Если и вторая попытка неудачна — выдаётся отказ, а не
сомнительный ответ.

### Цитаты

Цитаты формируются из фрагментов, на которые модель действительно
сослалась; остальные отобранные фрагменты добавляются как дополнительные
источники. Каждая цитата содержит документ, редакцию, номер пункта,
страницу, процент релевантности и точный текст положения.

Текст фрагментов дублируется в PostgreSQL: цитата показывает точную
формулировку пункта даже при недоступности векторного хранилища.

## Потоковый режим

В `POST /chat/stream` поиск и переранжирование выполняются до начала
потока, поэтому цитаты известны заранее и отправляются первым событием —
сотрудник видит источники уже во время генерации текста.

Критик в этом режиме не запускается: он требует второго вызова модели, что
лишает стриминг смысла. Барьер по релевантности работает до генерации, а
полный контур с критиком доступен в `POST /chat`.
