# Разграничение доступа и защита информации

## Ролевая модель

Роли отражают реальные функции в Центре документационного обеспечения,
а не технические уровни доступа.

| Роль | Назначение | Ключевые права |
|---|---|---|
| Сотрудник | Повседневная работа с требованиями | задать вопрос, сформировать черновик, проверить проект документа |
| Методолог ЦДО | Сопровождение базы знаний | загрузка редакций, управление версиями и шаблонами, запуск оценки качества |
| Аудитор | Контроль | чтение журнала действий и чужих диалогов, метрики; правка базы знаний недоступна |
| Администратор | Администрирование | полный доступ, включая управление учётными записями |

Права описаны как атомарные разрешения (`backend/app/core/rbac.py`).
Добавление роли не требует изменения кода эндпоинтов — меняется только
матрица соответствия ролей и прав.

## Разграничение по грифу документа

Независимо от прав на действия, каждому фрагменту базы знаний присвоен
гриф: общедоступно / для внутреннего пользования / ограниченный доступ.
Роль имеет потолок допуска.

**Ключевое решение:** фильтр по грифу применяется на уровне запроса к
векторному хранилищу. Недоступные сотруднику положения не попадают ни в
результаты поиска, ни в контекст языковой модели. Это принципиально
надёжнее, чем фильтрация выдачи после генерации: модель физически не
получает закрытые данные и не может их пересказать.

## Защита корпоративных данных при использовании LLM

1. **Модель работает внутри контура.** Ollama, эмбеддер и реранкер
   развёрнуты локально. Обращений во внешние API нет ни на одном этапе,
   включая оценку качества через RAGAS — судьёй выступает та же локальная
   модель.
2. **Сетевая изоляция.** PostgreSQL, Redis и Qdrant вынесены в сеть
   `br_net` с флагом `internal: true`: у них нет ни опубликованных портов,
   ни выхода в интернет. Наружу выставлен единственный порт Nginx.
3. **Маскирование в логах.** Процессор structlog вычищает ФИО, адреса
   электронной почты, телефоны, номера документов и СНИЛС как по списку
   ключей, так и регулярными выражениями в свободном тексте.
4. **Журнал без содержания.** В аудит пишется факт действия, но не текст
   обращения: вопросы и ответы могут содержать персональные данные.
5. **Временное хранение черновиков.** Загруженные на проверку файлы
   удаляются сразу после извлечения текста; сформированные черновики
   живут 7 дней и удаляются фоновой задачей.
6. **Метрики не выставлены наружу.** Эндпоинт `/metrics` подключён
   в корень приложения, а Nginx проксирует только `/api/`, поэтому
   из интернета он недостижим в принципе — Prometheus обращается к нему
   по внутренней сети. Состав моделей и показатели базы знаний для экрана
   администратора отдаёт отдельный авторизованный эндпоинт
   `GET /api/v1/admin/system/health` с правом `metrics:read`.

## Аутентификация

### Расхождение с исходным ТЗ

ТЗ предполагало валидацию JWT в Nginx. Директива `auth_jwt` доступна
только в коммерческой редакции NGINX Plus, что противоречит требованию
«решение на open source».

**Принятый компромисс:** Nginx отвечает за ограничение частоты запросов,
терминацию TLS и заголовки безопасности. Проверка подписи токена, срока
действия, издателя, типа и факта отзыва выполняется в зависимостях
FastAPI через `python-jose`.

### Реализованные меры

- Пароли хранятся как bcrypt-хеши (12 раундов), парольная политика
  проверяется при создании и смене.
- Access-токен живёт 60 минут, refresh — 7 дней с ротацией: использованный
  refresh-токен отзывается немедленно.
- Отзыв токенов — denylist в Redis по `jti` с временем жизни, равным
  остатку срока действия самого токена.
- Счётчик неудачных входов с блокировкой учётной записи после 7 попыток.
- Ответ при неверном пароле и при несуществующем пользователе одинаков:
  перечисление учётных записей по коду ответа невозможно.
- Смена пароля отзывает текущий токен.

### Ограничение частоты

Зоны Nginx разделены по характеру операции: вход — 5 запросов в минуту,
диалог — 20, загрузка файлов — 10, остальное API — 60. Дополнительный
контур на стороне приложения (`slowapi`) работает поверх Redis и
сохраняется при обходе прокси.

## Путь к промышленному контуру

- Аутентификация переносится на `oauth2-proxy` или Keycloak с
  подключением к корпоративному каталогу; проверка прав в приложении
  остаётся без изменений.
- Секреты переезжают из `.env` в Vault или в секреты оркестратора.
- Добавляется взаимная TLS-аутентификация между сервисами внутреннего
  контура.
- Журнал действий выгружается в корпоративную SIEM.
