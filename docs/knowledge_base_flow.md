# Схема взаимодействия с инструкцией и базой знаний

## Жизненный цикл документа

```
   Методолог ЦДО
        │
        │ 1. Регистрирует документ (код, название, гриф)
        ▼
  ┌─────────────────────┐
  │ knowledge_documents │  INSTR-DOC, MATRIX-APPROVAL, GUIDE-MODULES, FAQ-PORTAL
  └──────────┬──────────┘
             │ 2. Загружает файл редакции
             ▼
  ┌─────────────────────┐     хеш содержимого совпал?
  │  document_versions  │────── да ──→ новая версия не создаётся
  └──────────┬──────────┘
             │ 3. Celery: индексация
             ▼
   ┌────────────────────────────────────────────┐
   │ Загрузка → Нарезка по пунктам → Векторы    │
   └──────────┬─────────────────────┬───────────┘
              │                     │
              ▼                     ▼
   ┌──────────────────┐   ┌────────────────────┐
   │ document_chunks  │   │      Qdrant        │
   │  (PostgreSQL)    │◄─►│ dense + sparse,    │
   │  точный текст    │ id│ payload с грифом   │
   │  пунктов         │   │ и признаком версии │
   └──────────────────┘   └────────────────────┘
              │ 4. Активация редакции
              ▼
   is_active = true в PostgreSQL
   is_active_version = true в payload Qdrant
   сброс кеша ответов в Redis
```

### Общий идентификатор фрагмента

Запись в `document_chunks` и точка в Qdrant создаются с **одним и тем же
идентификатором**. Это не косметика: цитаты в ответе приходят из payload
векторного хранилища, а `message_citations.chunk_id` — внешний ключ на
`document_chunks.id`. При разных идентификаторах сохранение ответа
с цитатами нарушало бы ссылочную целостность, то есть падало бы на
каждом содержательном ответе.

При сохранении цитат существование фрагментов дополнительно проверяется
одним запросом: после переиндексации в Qdrant могут остаться точки,
которых уже нет в PostgreSQL. Текст положения хранится в самой цитате,
поэтому ответ остаётся проверяемым даже без ссылки на фрагмент.

### Что происходит при загрузке

| Шаг | Что делает |
|---|---|
| Разбор | pdfplumber с отбрасыванием символов светлой заливки — водяной знак иначе попадает внутрь слов |
| Таблицы | извлекаются отдельным проходом, помечаются блоком `[Таблица]` |
| Нарезка | по границам пунктов; короткие объединяются с сохранением всех номеров |
| Векторизация | bge-m3 (плотный) + BM25 по словарю корпуса (разреженный) |
| Словарь BM25 | сохраняется в том `backend_artifacts`; процесс API перечитывает его по времени изменения файла |
| Payload | гриф, код документа, редакция, признак действующей версии, номер пункта и список объединённых пунктов |

## Версионность

Требование слайда 4 ТЗ: решение должно предусматривать версионность и
возможность актуализации документов.

**Что реализовано:**

- Загрузка нового файла создаёт **новую редакцию**; прежняя сохраняется
  целиком, включая векторы в Qdrant.
- Повторная загрузка того же содержимого распознаётся по SHA-256 и не
  плодит версии.
- Действующая редакция ровно одна. Гарантируется частичным уникальным
  индексом в PostgreSQL (`uq_active_version_per_document`) и флагом
  `is_active_version` в payload Qdrant.
- Поиск по умолчанию идёт только по действующим редакциям, но архивные
  доступны для сравнения: можно показать, как требование выглядело раньше.
- **Откат выполняется без переиндексации** — меняется только флаг
  действующей редакции. Операция занимает доли секунды.
- При смене редакции сбрасывается кеш ответов: прежние ответы могли
  ссылаться на неактуальные формулировки.

**Демонстрация на защите:**

```bash
docker compose exec backend python -m app.workers.cli versions INSTR-DOC
docker compose exec backend python -m app.workers.cli activate INSTR-DOC 1
```

Между командами задаётся один и тот же вопрос — ответ меняется вместе с
редакцией инструкции.

## Подключение новых источников

Код при этом не меняется:

1. Зарегистрировать документ: `POST /api/v1/admin/knowledge/documents`
   либо добавить запись в `app/db/seed.py`.
2. Загрузить файл: `POST /api/v1/admin/knowledge/upload`.
3. Индексация запускается автоматически.

Поддерживаются PDF, DOCX, TXT, Markdown и HTML. Для PDF сохраняются номера
страниц, таблицы извлекаются отдельно — это важно для матрицы согласования.

Расширение на другие процессы (не только документооборот) выполняется тем
же путём: новый документ получает свой код и гриф, а маршрутизатор
обращений дополняется соответствующим намерением.

## Реестр шаблонов

Шаблоны модульных документов хранятся в таблице `document_templates`.
Каждая запись описывает:

- схему полей (`fields_schema`) — по ней агент понимает, что спросить
  у сотрудника, и в какой формулировке;
- маршрут согласования (`required_approvals`) — выдержка из матрицы;
- связанные пункты инструкции (`related_clauses`) — на них ссылается
  сформированный документ.

Добавление шаблона — запись в таблицу плюс файл бланка в
`data/templates/`. Если файла нет, документ собирается структурно по схеме
полей: оформление проще, но документ пригоден к работе. Это позволяет
демонстрировать генерацию до получения оригинальных бланков.
